1. 무엇이 신선한가 — 훅을 시스템으로 만들기

"내가 몬스터 쪽"이라는 반전은 소재만으로는 30분이면 소모됩니다. 이 반전이 계속 작동하는 시스템이 되려면, RPG의 익숙한 문법을 뒤집는 장치가 규칙 안에 들어가야 합니다. 세 가지를 축으로 잡았습니다.

훅 1 — 모험가는 죽지 않는다. 레벨업해서 돌아온다 격퇴당한 모험가는 사라지지 않고 마을로 돌아가 레벨을 올려 다시 옵니다. 이름을 가진 개체로 세이브에 남습니다. 플레이어 입장에서 "저 기사 놈 또 왔네, 이번엔 레벨 12"가 성립합니다. 플레이어가 모험가였을 때 당연하게 여기던 "죽어도 마을에서 부활" 규칙이, 이제는 나를 괴롭히는 규칙이 됩니다. 반전이 농담이 아니라 게임 시스템이 되는 지점.
훅 2 — 노획한 장비를 내 부하에게 입힌다 KayKit은 무기·방패가 캐릭터와 별개 모델입니다(Adventurers 25종+, Skeletons 10종+). 즉 모험가를 격퇴하고 떨군 검을 스켈레톤 손에 붙이는 것이 그래픽 추가 없이 실제로 화면에 보입니다. 이건 에셋 구조가 먼저 허락해 준 메커니즘이라 반드시 살려야 합니다.
훅 3 — 죽이지 말고 생포해서 전향시킨다 감옥에 가둔 모험가는 시간이 지나면 내 편이 됩니다. Adventurers 모델 5종이 적이면서 동시에 아군으로 재사용됩니다. 무료 티어 캐릭터가 9종(모험가 5 + 스켈레톤 4)뿐인 제약을, 오히려 "전향"이라는 서사로 바꿔 쓰는 설계.

2. 한 줄 정의와 장르

한 줄 — 방을 파고 함정을 놓고 스켈레톤을 세워, 몇 번이고 다시 찾아오는 모험가 파티를 막아내는 던전 경영 게임.

장르 — 던전 경영 시뮬레이션 × 타워 디펜스 하이브리드, 저장형(세이브 지속·게임오버 없음)

세션 길이 — 건설 3~5분 + 침입 1~2분 = 한 사이클 약 5~7분. 끊어 하기 좋음.

목표 플레이타임 — 12~20시간(방 6종×3티어, 함정 4종×3티어, 부하 승급 트리, 모험가 숙적 20명)

3. Core Loop

굴착 · 방 배치→부하 배치 · 장비 장착→함정 설치→ 침입 페이즈 (자동 전투 + 개입)→정산: 노획 · 골드 · 생포→ 연구 해금 · 위협도 상승→반복

이 루프에서 플레이어가 내리는 결정은 세 층위입니다. 즉시 결정(어디에 함정을 놓나) / 사이클 결정(위협도를 올릴까 유지할까) / 장기 결정(연구를 방 쪽으로 갈까 부하 쪽으로 갈까). 세 층위가 다 있어야 12시간이 버팁니다.

4. 던전 그리드 — 게임의 뼈대

12×12 격자로 시작해 확장 연구로 최대 24×24. 타일 종류는 5가지뿐입니다.

타일설명에셋
암반미개척. 굴착 비용을 내면 통로가 됨Dungeon Pack 바위·벽
통로모험가 이동 경로. 함정 설치 가능바닥 타일 + 벽 모듈
방2×2 이상 공간. 기능 부여바닥 + 방별 프롭
입구고정. 모험가가 들어오는 지점문 · 계단
코어고정. 여기 도달하면 침입 성공(플레이어 손해)제단 · 배너
핵심 전략축 — 경로 길이 vs 굴착 비용 모험가는 입구에서 코어까지 최단 경로로 이동합니다(A*). 통로를 구불구불하게 파면 이동 거리가 길어져 함정과 부하가 붙을 기회가 늘지만, 굴착 비용과 유지비가 듭니다. 반대로 짧고 굵게 막는 요새형도 성립합니다. 보물방은 이 축을 조작하는 도구입니다 — 모험가는 탐욕 수치가 높으면 최단 경로를 벗어나 보물방에 들릅니다. 즉 플레이어가 미끼로 경로를 유도할 수 있습니다. 이게 "던전을 설계한다"는 감각의 핵심.

5. 방 시스템

방은 2×2 이상의 통로 블록에 기능을 부여해 만듭니다. 전부 Dungeon Pack 프롭으로 표현됩니다.

방효과전략적 역할사용 프롭
보물방골드 생산 + 모험가 유인(경로 우회)위협도를 올리고 경로를 조작하는 양날의 방보물상자 · 금화 · 받침대

작업장노획 장비 수리·강화, 함정 재장전 속도장비 빌드의 엔진탁자 · 모루 · 상자
감옥생포한 모험가 수용, 시간 경과 후 전향훅 3의 구현체. 느리지만 최상급 부하 획득창살 · 사슬 · 통

6. 부하 — Skeletons 4종

KayKit Skeletons 무료 티어는 Warrior / Rogue / Mage / Minion 4종입니다. 4종밖에 없다는 제약을 장비와 배치로 확장합니다.

Skeleton Warrior — 차단

통로를 막고 버팁니다. 좁은 통로에 세우면 뒤의 파티가 통과하지 못합니다. 방패 장착 시 원거리 저항.

Skeleton Rogue — 기습

은신 배치. 파티가 지나간 뒤에서 나타나 후방의 메이지·레인저를 노립니다. 배치 위치가 곧 실력.

Skeleton Mage — 후열

방 안쪽에서 원거리 공격. 통로가 길수록 유효 타수가 늘어납니다. 경로 설계와 직접 연동.

Skeleton Minion — 물량

비용이 싸고 약합니다. 함정 발동 유도, 시간 벌기, 로그의 함정 해제를 방해하는 용도.

성장 — 전투 경험치로 레벨업, 무기 슬롯 1 + 방어구 슬롯 1. 노획한 모험가 장비를 그대로 장착하며 모델이 실제로 바뀝니다. 쓰러져도 영구 손실 없이 제단에서 부활(저장형 원칙: 잃는 것은 시간뿐).

7. 모험가 — 지속되는 숙적

이 게임에서 가장 신선한 부분이자, 반드시 제대로 만들어야 하는 시스템입니다.

직업행동플레이어가 대응해야 하는 것
Knight선두. 방어력 높고 함정 피해를 대신 받음화력 집중 또는 우회 유도
Barbarian벽·문을 부수고 지름길을 뚫음경로 설계가 무력화될 수 있음 — 두꺼운 벽 연구 필요
Rogue함정을 탐지·해제미니언으로 방해하거나 함정을 이중으로
Mage원거리 광역. 미니언 무리를 지움물량 빌드의 천적
Ranger후방에서 부하를 저격로그로 후열을 끊어야 함

숙적 사이클

파티 편성 (서버)→침입→격퇴→ 마을 귀환 · 레벨업 · 장비 교체→재도전 (더 강해져서)

각 모험가는 {id, 이름, 직업, 레벨, 장비, 상태, returnsAt}로 세이브에 남습니다. 20명 내외의 명단이 유지되고, 플레이어는 특정 개체를 기억하게 됩니다. 격퇴 대신 생포하면 명단에서 빠지고 감옥으로 이동합니다 — 숙적을 영구히 없애는 유일한 방법이 "죽이는 것"이 아니라 "내 편으로 만드는 것"이라는 점이 훅과 정확히 맞물립니다.

8. 침입 페이즈 — 개입 수준

완전 자동 관전은 지루하고, 실시간 부하 조작은 모바일에서 무너집니다. 중간값을 잡았습니다.

  • 전투는 자동 진행. 플레이어는 3개의 워든 스킬만 씁니다(각각 쿨다운).
    • 어둠의 가호 — 지정 범위 부하 회복 + 잠시 무적
    • 집결 — 부하를 지정 타일로 재배치(전투 중 유일한 위치 조작)
    • 강제 발동 — 함정을 즉시 터뜨림(로그가 해제하기 전에)
  • 배속 1× / 2× / 4× 토글. 반복 침입을 빠르게 넘길 수 있어야 저장형 게임의 후반이 버팁니다.
  • 버튼이 3개+배속뿐이라 PC와 모바일이 완전히 같은 게임이 됩니다.

9. 실패 처리 — 게임오버 없음

모험가가 코어에 도달하면:

  • 보관 골드의 일부를 약탈당함 (창고 방이 피해를 줄임)
  • 경로상 함정이 파괴됨 (재설치 필요)
  • 쓰러진 부하는 기절 상태로 제단에서 부활
  • 던전 구조 · 부하 레벨 · 연구 · 도감은 전부 유지

즉 손실은 항상 골드와 시간으로 환산되고, 진행이 뒤로 가지 않습니다. 이게 이번 기준(저장형)의 핵심 원칙이고, 런 기반 로그라이트와 갈리는 지점입니다.

10. 위협도 — 플레이어가 쥔 난이도 손잡이

위협도가 오르면 더 강한 파티가 오고 노획도 좋아집니다. 위협도는 자동으로만 오르지 않고 플레이어가 조절합니다.

  • 보물방을 늘리면 위협도 상승 (부유한 던전은 소문이 남)
  • 모험가를 죽이면 상승, 생포하면 완만히 상승
  • 일정 기간 조용히 있으면 서서히 하락

"준비가 안 됐으면 위협도를 낮춰 시간을 번다"가 가능해야 저장형 게임에서 벽에 막히지 않습니다.

13. Verse8 연동 — 공식 API 기준

문서에서 확인한 사실 (추측 아님)
  • 서버 코드는 isolated-vm에서 실행 → fs, http, axios 등 Node 내장/외부 IO 모듈 사용 불가. 순수 JS/TS와 $sender, $global, $room, $asset만 사용 가능.
  • 단일 server.js(루트, class Server{}, export 금지) 또는 구조화 프로젝트 server/src/server.ts 사용 가능. 후자를 쓰되 Handler 네임스페이스는 쓰지 않음(클라 호출이 remoteFunction('game.x')로 바뀌어 이득 없음).
  • setTimeout/setInterval 금지 — 대안은 $roomTick이지만 이 게임은 룸이 없으므로 아예 불필요. 부하 부활·모험가 귀환은 전부 타임스탬프 + 접속 시 계산으로 처리.

VXShop사용 (구현됨)상품 remove_ads(Lifetime 1회) — 인터스티셜 영구 제거. 클라이언트 useVXShop().buyItem(), 지급은 서버 $onItemPurchased({account, purchaseId, productId, quantity})에서만. 선행조건: CPP 가입 + 게임 배포 — 현재 미충족이라 실구매 테스트 불가

14. 세이브 스키마

// $global.updateMyState(...) 로 저장되는 구조
{
  version: 1,

  grid: { w: 12, h: 12, cells: "RLE 문자열" },   // 타일 타입만
  rooms:  [{ type: "treasury", x, y, w, h, level }],
  traps:  [{ type: "spike", x, y, charges, readyAt }],

  minions: [{ id, type: "warrior", level, exp,
              weaponId, armorId, homeTile: {x,y}, revivesAt }],

  loot:    { weapons: [{ id, srcClass: "knight", tier }],
             armors:  [{ id, tier }] },

  prisoners: [{ advId, convertsAt }],

  adventurers: [{ id, cls: "ranger", name, level,
                  gear: [ids], state: "town"|"raiding"|"captured",
                  returnsAt }],

  threat, wavesRepelled, coreBreaches,
  research: ["deep_walls", "barracks_2", ...],
  lastSeenAt
}
// 골드는 여기 없음 → $asset('gold')
설계 근거 두 가지
  • 골드를 스테이트에서 뺀 이유 — 문서가 화폐·자원은 $asset을 쓰라고 명시. 세이브와 화폐가 분리되면 세이브 조작으로 돈을 늘리는 경로가 막힙니다.
  • 그리드를 RLE로 저장하는 이유 — 24×24까지 커지면 셀 배열이 세이브에서 가장 큰 덩어리가 됩니다. 타일 종류가 5개뿐이라 RLE 압축률이 매우 높습니다. 전체 세이브를 8~15KB 수준으로 유지하는 것이 목표.

저장 시점

  • 즉시 저장 — 건설 확정, 침입 종료, 연구 완료, 장비 장착 (의미 있는 체크포인트)
  • 주기 저장 — 60초 오토세이브 (건설 페이즈에서 조작이 이어질 때)
  • 이탈 저장 — visibilitychange / pagehide

이유: remoteFunction 표준 호출이 약 10회/초 제한이라 클릭마다 저장하면 안 됩니다. 중간 조작은 클라 메모리에만 두고 위 3개 시점에서만 서버로 보냅니다.

15. 서버 검증 — 어디까지 믿을 것인가

저장형은 자원 수치가 곧 게임이라, 클라가 보낸 결과를 그대로 받으면 무의미해집니다. 전투 전체를 서버에서 재실행하는 건 isolated-vm 비용상 과합니다. 3단 절충을 씁니다.

  1. 파티는 서버가 만든다 — startRaid() 호출 시 서버가 위협도와 모험가 명단을 근거로 파티 구성 + 시드를 발급. 클라가 "쉬운 파티"를 스스로 고를 수 없음.
  2. 결과는 범위로 검증 — 서버가 배치 데이터(부하 수·레벨·함정 수·경로 길이)로 기대 노획 상한을 계산. 클라 보고가 상한을 넘으면 거부하고 상한값으로 클램프.
  3. 지급은 서버가 한다 — 골드는 클라가 더하는 게 아니라 서버가 $asset.mint()로 지급. 클라는 "요청"만 함.

결정론적 틱을 쓰기 때문에, 나중에 의심스러운 계정만 골라 시드로 서버 재시뮬하는 것도 가능합니다(MVP 범위 밖).

18. 확정된 설계 결정

세 분기 모두 확정되었습니다. 아래는 확정에 따라 추가로 고정된 규칙입니다.

확정 1 — 개입 수준: 워든 스킬 3개 + 배속 전투는 자동. 플레이어는 어둠의 가호 / 집결 / 강제 발동 3개 스킬과 1×·2×·4× 배속만 조작합니다.
→ 파생 규칙: 스킬은 마나가 아니라 개별 쿨다운으로 관리합니다(자원 관리 층을 하나 더 얹으면 자동 전투의 가벼움이 사라짐). 쿨다운은 침입 페이즈 시작마다 초기화하고, 제단·병영 레벨로 단축됩니다. 스킬 사용 여부는 결정론적 틱에 이벤트로 기록되어 리플레이·서버 재시뮬과 호환됩니다.
확정 2 — 감옥·전향 시스템 포함 생포한 모험가는 감옥에 수용되고, 시간이 지나면 내 부하가 됩니다.
→ 파생 규칙(생포 조건을 명확히 정의해야 하므로):
  • 제압 상태 — 모험가 HP가 0이 되면 즉사가 아니라 제압(downed) 상태로 3초간 쓰러져 있습니다.
  • 이 3초 안에 감옥에 빈 자리가 있고 근처에 부하가 있으면 자동으로 끌고 갑니다 → 생포.
  • 3초가 지나거나 감옥이 꽉 찼으면 사망 처리 → 장비를 떨구고(노획) 마을로 귀환해 레벨업 후 재도전.
  • 즉 노획(장비) ↔ 생포(인력)는 배타적 선택입니다. 감옥 자리를 늘릴지, 장비를 더 모을지가 빌드 선택이 됩니다. 훅 2와 훅 3이 서로 경쟁하게 만들어 둘 다 살아남습니다.
  • 전향까지 걸리는 시간은 모험가 레벨에 비례(convertsAt 타임스탬프). 전향한 모험가는 원래 직업 성능을 유지한 채 내 부하 슬롯을 차지합니다.
확정 3 — 탑다운 쿼터뷰 3D 고정 각도(약 45°) 직교 투영에 가까운 원근 카메라. Q/E 90° 회전으로 4방향만 지원해 벽 가림을 해결합니다.
→ 파생 규칙: 카메라 방향 기준으로 앞쪽 벽만 낮춰 렌더(높이 스케일 0.3)해 내부가 보이게 합니다. 벽 모델을 자르지 않으므로 KayKit 모듈 구조를 그대로 씁니다.
